# Prepare explicitly disposable checkout output directories before execution

## Context and Problem Statement

A launched producer can fail before replacing a previous execution's report.
Collection then copies old bytes into the new attempt's distinct archive without
changing its failed runtime outcome. The issue's native investigation reproduced
this; emptying the source under its output lock preserved current partial evidence
and the earlier archive. Existing Playwright preparation wiring works, but repeats
a script, job and dependency edge in every project. Runner initialization can be
too late when compilation or startup fails first.

## Considered Options

- Explicit preparation of disposable output directories under existing locks.
- Keep application preparation jobs: sufficient today, but retains the boilerplate
  this change is intended to remove. Runner cleanup alone misses earlier failures.
- Allocate new source directories per attempt: isolates sources but changes path
  references, mounts and source retention beyond the requested stable directory.
- Infer freshness from hashes or timestamps: cannot establish production by this
  execution, including a freshly generated byte-identical report.
- Arbitrary hooks or a cleanup framework: add authority and lifecycle machinery
  unnecessary for emptying one declared directory.

## Decision Outcome

Add one optional output setting to remove and recreate its directory empty before
each new execution, creating it if absent. Omission preserves existing behavior.
The declaration, rather
than artifact naming or inferred filesystem ownership, grants deletion authority
over that scratch subtree only; it never adopts retained resource ownership.

Prepare each selected opted-in directory once, after acquiring all selected output
locks and before launching any component, for both persistent and disposable work.
Joining accepted work, offline planning and metadata preparation do not clear it.
Compatible new starts and explicit restarts prepare again after prior owners and
collectors join. Healthy starts keep accepted settings and report drift; later
attempts may accept a changed opt-in through existing compatibility rules. Resource
initialization stamps remain unchanged: a skipped fresh-only job does not repopulate
an emptied output or claim artifacts. Use each-start producers for repeatable files.

Revalidate source identity, output paths and consumer conflicts under the acquired
locks before deletion. Require a strict manifest-directory descendant with safe
relative syntax and a directory or absent target. Reject symlink components on
the path, including internal aliases, and use root-relative filesystem operations;
never follow links found inside the disposable tree. Reject overlap with this
daemon's private state and retained resource data, and with Git metadata, including
filesystem aliases.
Inspection or validation uncertainty fails closed. Preflight all selected targets
before the first removal; no component launches unless every preparation succeeds.

Where an opted-in declaration overlaps another output declaration, allow only the
same directory, concurrency group and opt-in; deduplicate its preparation. Reject
nested or mixed-policy overlaps even in one group, across scene declarations.
Keep ordinary output overlap rules unchanged. Preserve active, kept and uncertain
consumer fences across retained/current plans and changed groups; locks remain held
through collection and joined cleanup. Cancellation observed while waiting or before
preparation causes no deletion. Once removal starts it can be partial: cancellation
or filesystem failure launches nothing, records the existing failed/cancelled attempt
outcome and retains or releases locks under existing keep/cleanup rules. Do not
roll back deleted scratch files, replay preparation during recovery or retry
automatically; a later explicit new execution prepares again.

Keep collection semantics: unlaunched/skipped producers claim nothing; launched
producers may retain partial evidence, while missing declared sources fail collection.
Earlier archives remain governed by existing retention, never output preparation.
An empty starting directory does not establish report finalization or attribute
bytes written by undeclared external processes. This remains cooperative checkout
execution, not containment against hostile filesystem mutation or mount manipulation.

### Consequences

The Playwright recipe can remove its cleanup script and preparation-only component.
Authors opt into irreversible deletion of the whole scratch directory, even if a
later dependency fails or its producer is skipped. There is no transaction spanning
multiple directories; some may be empty after preparation fails.

The optional declaration travels through existing shared plans, snapshots and
acceptance writers; absent historical values mean disabled. No new journal, state
migration, endpoint, worker, timer, dependency or cleanup mode is required. Safe
deletion and overlap validation are the substantive maintenance cost. Existing
consumer fences and cooperative native cleanup limits still apply; protecting
arbitrary external consumers would require a separate decision.
